# Ubuntu 内核兼容方案总结

这组改动可以不按“提交”来理解，而按“三层方案”来理解：

1. 先解决 Ubuntu 24 内核下 BPF LSM 程序加载失败的根因。
2. 再把这套修复接进主仓库的构建、产物和验证链路。
3. 最后把兼容思路扩展到 Ubuntu 22.04 / 5.15，并给出后续演进方向。

如果只看结论，这套方案的核心是：

* Ubuntu 24 走“根因修复 + 主仓库同步”的路线。
* Ubuntu 22.04 / 5.15 走“保留通用修复 + 按目标内核 BTF 重建产物”的路线。
* 长期则演进到“按 hook 选择性加载”的路线，而不是继续依赖整套对象一次性加载。

## 1. 要解决的到底是什么问题

这组工作的本质，不是单纯适配两个 Ubuntu 版本，而是解决同一类问题在不同内核上的两种表现：

* 某些 LSM hook 的函数原型会随内核变化。
* 某些 tail-call 组织方式在新内核上会触发更严格的约束。
* 某些路径检查逻辑在 verifier 看来过于复杂，会导致程序加载失败。

在 Ubuntu 24 上，这些问题集中表现为：

* `path_rename` 的 hook 原型发生变化。
* `path_link` 和 `path_rename` 共用同一个 tail-call program array 不再稳妥。
* `move_mount` 相关逻辑容易触发 verifier 压力。

在 Ubuntu 22.04 / 5.15 上，问题又变成另一种形式：

* 如果直接复用为 Ubuntu 24 生成的 `vmlinux.h`，那么 `path_rename` 的原型会与目标 5.15 内核不一致。

因此，真正要解决的不是“写死支持某个版本号”，而是把通用修复和内核特定部分分开处理。

## 2. 方案一：Ubuntu 24 的兼容方案

Ubuntu 24 的处理重点是先把 eBPF 程序本身修到能过加载和 attach。

这套方案包含三个关键动作：

### 2.1 对齐 `path_rename` 的 hook 原型

Ubuntu 24 的 `path_rename` 比旧内核多一个 `flags` 参数。如果编译期假设还是旧原型，那么程序在加载或 attach 时就可能直接失败。

所以第一步是让编译期看到的 hook 原型与 Ubuntu 24 当前内核保持一致。

### 2.2 拆分 `path_link` 和 `path_rename` 的 tail-call program array

原先把两个 hook 的 tail program 放在同一个 prog array 里，属于“早期能工作，但兼容边界不稳”的实现方式。到了 Ubuntu 24，这种组织方式更容易成为加载失败点。

因此方案改成：

* `path_link` 使用自己的 prog array。
* `path_rename` 使用自己的 prog array。

这样可以把不同 hook 的 tail-call 语义隔离开，减少对象整体加载失败的风险。

### 2.3 降低 `move_mount` 相关 verifier 压力

对于 `move_mount` 这一类本身就比较敏感的路径检查逻辑，继续强制内联会增加 verifier 的复杂度判断压力。

因此方案中把关键路径检查从强制内联改为非内联，让 verifier 更容易接受这段逻辑。

### 2.4 让修复真正进入主仓库构建链路

仅仅修 eBPF 子仓库还不够。只要主仓库构建链路、镜像构建、生成产物同步没有跟上，本地重新构建时就仍然可能重新编出旧对象。

所以 Ubuntu 24 方案的完整形态不只是“代码修好了”，而是：

* 主仓库要跟上新的子模块基线。
* 主仓库要同步新的生成产物。
* 构建入口和说明文档也要一起更新。

只有这样，Ubuntu 24 的兼容修复才算真正落地。

## 3. 方案二：Ubuntu 22.04 / 5.15 的兼容方案

Ubuntu 22.04 / 5.15 的关键点是，不能把 Ubuntu 24 的默认头文件直接拿来复用。

这里最容易犯的错是：看到 Ubuntu 24 修好了，就以为这套生成物天然也兼容 5.15。实际上并不是这样，因为 5.15 的 `path_rename` 仍然是旧原型。

所以这条方案的核心不是“回退 Ubuntu 24 修复”，而是“保留通用修复，只重建与目标内核强相关的部分”。

### 3.1 保留通用修复，不回退

下面这些修复对 5.15 仍然是有价值的：

* `path_link` 和 `path_rename` 分离 tail-call program array。
* 降低 `move_mount` 相关 verifier 压力。

这些都属于通用稳定性改进，不应该因为目标内核变成 5.15 就退回去。

### 3.2 用目标内核 BTF 重建 `vmlinux.h` 和 BPF 产物

真正需要跟着目标内核变化的，是 `vmlinux.h` 所描述的 hook 原型，以及基于它编出来的对象文件。

因此这条方案的落点变成：

* 从目标节点的 BTF 重新生成 `vmlinux.h`。
* 再基于这份头文件重新编译 BPF 产物。

也就是通过下面这种方式，把“当前内核是谁”明确传进构建流程：

```bash
make VMLINUX_BTF=/sys/kernel/btf/vmlinux build-ebpf copy-ebpf local
```

这条命令背后的含义是：

* 通用逻辑继续沿用当前基线。
* 与内核签名强相关的部分按目标节点现状重建。

这才是 Ubuntu 22.04 / 5.15 的正确兼容方式。

## 4. 统一落地方式

把 Ubuntu 24 和 Ubuntu 22.04 / 5.15 放在一起看，会发现它们最终落地方式其实是一致的，只是“重建的必要程度”不同。

统一流程可以概括为四步：

1. 确认节点满足基础条件，包括启用 BPF LSM、存在可读 BTF、运行时版本满足要求。
2. 在本地按正确基线构建 `bin/vArmor` 和所需 BPF 产物。
3. 通过镜像流程或现场替换方式把新二进制真正部署到节点上。
4. 重启 `varmor-agent`，再用日志、DaemonSet 状态和最小策略验证确认程序已经真正生效。

如果采用现场验证方式，最重要的不是“文件拷进去了”，而是：

* 节点上实际运行的二进制已经替换成功。
* agent 已经重启并重新加载新的对象。
* 日志中不再出现 `path_rename` 和 `move_mount` 的典型加载失败错误。
* 最小 BPF 策略能够真正命中目标容器。

## 5. 长期方案：从整包加载走向 Selective Load

这组改动并不只是在修两个兼容问题，也顺手暴露了当前加载模型的局限：

* 现在是一整套对象一起加载。
* 某一个高风险 hook 出问题，可能把整套对象都拖垮。
* 即使当前 profile 实际只用到少数 hook，也会把全部 hook 一起加载。

因此长期方向不是继续堆更多静态兼容分支，而是推进 Selective Load：

* 共享 maps 和变量继续常驻。
* 程序按 hook 粒度按需加载。
* 高风险 hook 提供多个 variant，并在运行时试探当前内核能接受哪一个实现。

这条路线的意义是把兼容问题从“整套对象失败”收敛为“单个 hook 的适配问题”，从而让系统在多内核环境下更稳。

## 6. 最终可以怎么理解这组方案

如果压缩成最短版本，可以这样理解：

1. Ubuntu 24 先修 eBPF 根因，再同步主仓库构建链路。
2. Ubuntu 22.04 / 5.15 不回退这些通用修复，而是按目标内核 BTF 重新生成内核相关头文件和对象。
3. 两条方案最终都要落到真实部署和最小策略验证上，不能只停留在“本地能编过”。
4. 长期要从版本特判转向按 hook 选择性加载，逐步把兼容风险缩小到单个 hook 级别。
